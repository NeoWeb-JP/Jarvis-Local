# Experimental VoicePipeline history correction

This candidate derives from `paulglavin/VoicePipeline` and includes its MIT licence. It is based on `/app/api/main.py` SHA-256 `83b8285bc91b451fcf1e1b80db141cf9d3f1620026186d7f511f128066e8c386` and `/app/ui/app.js` SHA-256 `e4156a695b1c6a20e8a1700a565b3070918174fd805d1fd9aeb87cb1066d7be1`. It is an isolated test candidate, not a release or an instruction to overwrite another version.

History provides a correction control for resolved or dismissed recordings. Changing the speaker appends a new resolution, removes the recording from other speakers' reference lists and leaves the selected speaker's reference list unchanged. Undo appends a dismissal event and returns the recording to Pending. Neither option deletes audio or automatically adds a reference. Previous resolutions remain in the audit trail; stale History tabs are rejected. The control asks for confirmation.

The original pipeline match and its confidence remain unchanged; the History summary shows a confidence only when it corresponds to the displayed speaker. Filters use the corrected assignment. These changes do not restore references previously rotated out by earlier incorrect assignments or recalculate historical interaction counts and averages. Audio paths must be available in the database to identify references safely. Cache invalidation is requested after saving; the service's existing scheduled refresh may take several minutes. A failure to request refresh is reported separately from a successful database correction.

`test_correction.py` uses temporary SQLite databases built from the upstream schema and extracts the candidate's real backend functions using Python AST; it does not start FastAPI. `test_ui.js` runs the History controls with a simulated DOM. An isolated live API, browser and voice test remains necessary.

`test_installer.py` exercises successful installation and a copy-failure rollback using fake Docker and temporary files; it never controls a real container. The original upstream files used by that test are included under `test_fixtures`.

`prepare-production.sh` is a staging-only preflight for a specific Compose deployment. It verifies the tested source and image hashes, renders the baseline and candidate Compose models privately, checks that only the intended read-only API and UI binds are added, checks existing live mount sources/access and the resolved image ID, and saves checksums for review. The script never recreates a container. It does not by itself prove that the current Compose environment or port configuration matches the already-running container, and it does not deploy the candidate. `test_prepare.py` exercises staging with fake Docker; `test_compose.py` exercises safe and unsafe model comparisons.

`check_runtime.py` compares the resolved baseline against the running container and image for environment, published ports, networks and common execution settings without printing environment values. It conservatively requests manual review for unsupported devices, security or resource settings. It does not prove every possible runtime property is identical. `test_runtime.py` covers matching and drift cases.

`check_post_deploy.py` checks that existing mounts remain unchanged and only the two intended read-only app files were added; it is not an audio or API health test.

`deploy-production.sh` accepts a previously verified staging directory, rechecks Compose and the running configuration, requires an explicitly reviewed sorted Docker writable-layer diff, saves a fresh private database snapshot and existing configuration copies, and recreates only the VoicePipeline service using the same image plus the extra override. It verifies mounts, common runtime settings, source hashes and the management API. If deployment fails after recreation begins, it attempts the original four-file Compose configuration only when the files and image still match. It never restores the database. It creates a Compose wrapper containing all five files; future Compose operations must include the extra override or use that wrapper.

`rollback-production.sh` removes only the extra app override by recreating the service with the original four files after verification. It preserves current data, speaker patches and threshold settings. It refuses to operate when the source configuration or image has changed. A rollback does not undo corrections already saved to the database. `test_deploy.py` checks deployment, preflight drift, failed deployment rollback and explicit rollback against a fake Docker environment. Neither script has been validated against every Docker configuration.
